**Goal:** close every spec section slice 1 left open, prove each against an example modelled on a shape our four real deployments actually have, and cut v0.1.0.

**Prerequisite:** slice 1 (`2026-08-07-slice-1-example-gallery.md`), Tasks 1–8. Task numbering here continues at 9.

**Architecture:** Seven tasks. Each pairs a missing tool feature with the example that proves it, because an example is how porter's schema is defined (a field with no example exercising it does not exist) and how an adopter starts.

## Global Constraints

Everything in slice 1's Global Constraints still binds. Additionally:

- **The FHS lint is total** (slice 1 Task 2): top level allowlisted to `usr/ etc/ opt/ lib/ var/`; every file *or symlink* under `etc/` must be declared a conffile; `env` never ships; `DEBIAN/` is porter's to construct and staging it raises; absolute symlinks are refused, relative in-stage ones are fine.
- **`assemble` returns its own `conffiles`** (slice 1 Task 4). Anything that stages files under `etc/` extends that list; it is never re-derived by a caller.
- **Prefer properties over prescribed implementations.** Slice 1's most detailed code prescriptions are exactly where its bugs came from — a `JUNK` list that would have refused every vendored interpreter, a `copytree` equivalence that does not hold, a validation that would have accepted a virtualenv. Each was caught by an implementer overriding the brief. These briefs state **what must be true and how to prove it**; choose the implementation and say why.

### Task 9: the `bake` stage — data built before packaging, and proven fresh

**Files:** create `src/porter/bake.py`, `tests/test_bake.py`, `examples/baked-data/`.

**Interfaces produced:** `bake(component, src_root) -> BakeResult` with `.ran: list[str]`, `.stamp: str`. `porter.yaml` gains a `bake:` block: `steps:` (list of commands run in `src_root`) and `artifacts:` (paths that must exist and be non-trivial afterwards).

**Why this exists.** leyes-cuba rebuilds its whole corpus before every package, then checkpoints SQLite's WAL, then stamps a build id — because beaver runs in WAL mode and a freshly-written database can live *entirely* in `<db>-wal`. Baking only `<db>` ships an empty database that works on the build host and is blank at the client. That is the canonical porter failure, and it has already happened once in real life.

**Properties to prove:**
- [ ] Each declared step runs in `src_root`, in order; a non-zero rc aborts the bake with the step named. **Read the rc directly.**
- [ ] Every declared artifact must exist **and exceed a declared minimum size** after baking. A magnitude check, not an existence check: an empty SQLite file exists.
- [ ] A SQLite artifact is refused when data is stranded in its WAL. Prove it by writing rows without checkpointing, asserting the bake refuses, then checkpointing and asserting it passes. This is the positive-control shape: the test must fail if the WAL check is removed.
- [ ] `bake` writes a provenance stamp (git SHA of `src_root` plus UTC timestamp) to **`usr/share/<pkg>/VERSION`** — package-owned, replaced on upgrade, inside the top-level allowlist. `assemble` carries it into the package so a client fault report can name the exact build. (une-tools does exactly this today: app, date, and the commits it was built from.)
- [ ] A component with no `bake:` block bakes trivially and is not an error.

**`examples/baked-data/`** — a service whose payload is a SQLite database built by a bake step, checkpointed, stamped, and asserted non-trivial. Its `porter.yaml` is the template an adopter copies.

### Task 10: migrations, and `<app>-setup`

**Files:** create `src/porter/migrate.py`, extend `config.py`, `tests/test_migrate.py`, `examples/stateful-service/`.

**Interfaces produced:** `migration_postinst(pkg, migrations: list[Migration]) -> str` where `Migration` has `.before_version` and `.script`. `setup_script(component) -> str` generating `/usr/bin/<pkg>-setup`.

**Why.** ainbox's installer runs its beaver 1.x→2.x migration `ALWAYS, not just on update` (line 522 of a 970-line script) because it cannot tell install from upgrade. dpkg can: `postinst` receives the previously-configured version as `$2`.

**Properties to prove:**
- [ ] On a **fresh install** no migration runs. `$2` is empty; a migration that fires here would run against a database that does not exist.
- [ ] On an upgrade **from below** `before_version`, the migration runs exactly once.
- [ ] On an upgrade **from at or above** it, the migration does not run.
- [ ] On a **re-install of the same version**, it does not run.
- [ ] A failing migration fails the `postinst`, leaving the package unconfigured rather than half-migrated and reported healthy.
- [ ] `<pkg>-setup` is interactive, idempotent and re-runnable; `postinst` still never prompts. Prove the postinst reaches no prompt under `setsid` with stdin closed, **with a control** showing a bare `read` does fail under that harness.

**`examples/stateful-service/`** — ships v1 with a state file, upgrades to v2 running a migration that rewrites it, and asserts the client's own data survived.

### Task 11: multi-service ordering

**Files:** extend `src/porter/systemd.py`, `tests/test_ordering.py`, `examples/multi-service/`.

**Why.** ainbox is 10 compose services with `depends_on`. systemd has no `condition: service_healthy` equivalent; ordering is `After=`/`Requires=` plus `Restart=on-failure` convergence. The spec records that as a deliberate behavioural change — this task makes it real and proves convergence actually happens.

**Properties to prove:**
- [ ] A component may declare `after: [other-component]`; the emitted unit carries `After=` and `Requires=` naming the *package's* unit, not the component's bare name.
- [ ] A declared cycle is refused at build time with both units named.
- [ ] `after:` referencing an undeclared component is refused.
- [ ] **Convergence, not just ordering:** with a dependency deliberately failing its first two starts, the dependent service still reaches `active` via `Restart=on-failure`. This needs real systemd — mark it `nspawn` and skip elsewhere, but write it.
- [ ] A single-component project emits no ordering directives at all (no ceremony where none is needed).

**`examples/multi-service/`** — three services, one depending on two others, modelling ainbox's shape at a size that runs in a test.

### Task 12: the `build:` escape hatch

**Files:** extend `src/porter/assemble.py`, `tests/test_escape_hatch.py`, `examples/custom-build/`.

**Why.** The spec calls this the thing that stops porter becoming "a second thing to fight": any component may declare `build: <script>` and take over the *assemble* stage while still getting FHS layout, lint, packaging, the gate and the repo for free. Without it, the first component that does not fit the schema forks the tool.

**Properties to prove:**
- [ ] A component with `build:` has its script run instead of the built-in assemble, receiving the stage path and the component's config as environment.
- [ ] Its output is linted, packaged, gated and published **exactly like any other** — the hatch bypasses assembly, not the guarantees. Prove by pointing a custom build at a stage that violates the FHS lint and asserting the build still fails.
- [ ] A non-zero rc from the script aborts with its stderr surfaced.
- [ ] The script cannot silently produce nothing: an empty stage is refused by magnitude check.

**`examples/custom-build/`** — a component whose payload is produced by a shell script rather than by porter's assembler.

### Task 13: shared interpreter package, and a bundled native binary

**Files:** extend `src/porter/assemble.py`, `src/porter/depends.py`, `tests/test_shared_interpreter.py`, `examples/native-binary/`.

**Why.** The interpreter is 97 MB before any dependency; ainbox's ten services bundling separately duplicate ~780 MB. And ainbox's engine ships a compiled `llama-server` plus hand-picked CUDA libraries — the case `Depends:` derivation exists for.

**Properties to prove:**
- [ ] `python: {package: <name>}` emits a **separate interpreter package**, and component packages `Depends:` on it by exact version.
- [ ] Installing a component from the USB repo pulls the interpreter package automatically, **offline**, and the service runs. This is the property that cannot be assumed — prove it with `--network none`.
- [ ] With `package: bundled` nothing changes from slice 1 (regression).
- [ ] A component declaring `native_binaries:` gets them staged under **`usr/lib/<pkg>/`** with the exec bit preserved, and `Depends:` derived from their ELF headers via `objdump` — **not `ldd`**, which executes the loader per file and hung a probe long enough to look like a deadlock.
- [ ] A native binary whose libraries do not resolve on the target is refused at build time, naming the missing sonames. Better a red build than a package that installs and cannot start.

**`examples/native-binary/`** — bundles a small real compiled binary and asserts its derived `Depends:` is non-empty and correct.

### Task 14: the real gate — `systemd-nspawn` and a signed repo

**Files:** extend `src/porter/gate.py`, `src/porter/repo.py`, `tests/test_nspawn_gate.py`.

**Why.** Slice 1 gates in Docker with `--network none`, which proves the payload, the upgrade and client-state survival but **not the unit under real systemd**. "The container answered" is not "the service came up". And `[trusted=yes]` means the client verifies nothing.

**Properties to prove:**
- [ ] The gate can run in `systemd-nspawn --private-network --ephemeral` against a rootfs obtained without `debootstrap` (absent on the build host — use `docker export`), install the `.deb`, and assert the **unit** reaches `active` and answers.
- [ ] The nspawn gate detects a unit that installs but fails to start — mutate the `ExecStart` and confirm the gate goes red. Without this the nspawn path is decoration.
- [ ] `repo.write_index` emits a detached signature; `install.sh` imports the key and drops `[trusted=yes]`.
- [ ] A **tampered** package in the repo is rejected by apt at install time. Flip a byte and prove it.
- [ ] Signing is optional: an unsigned repo still builds and installs, so a dev loop needs no key.

### Task 15: cut v0.1.0

**Files:** `README.md`, `CHANGELOG.md`, `pyproject.toml`, `AGENTS.md`, `know-how/`.

- [ ] `README.md` shows the real end-to-end flow with commands that work, and the shape table pointing at each example.
- [ ] `CHANGELOG.md` — 0.1.0 with the measured facts, not adjectives: glibc floor 2.35→2.41, peak transient 2× payload, apt adds no cache cost from a `file:` repo, split-config properties.
- [ ] `AGENTS.md` State reflects reality; the know-how index has an entry for anything done twice.
- [ ] **CI exists and arms the gate.** A GitHub Actions workflow running the full suite with `PORTER_REQUIRE_UV=1`. Slice 1 left that variable "real but unarmed" — off by default, so a `uv`-less run still exits 0 having skipped most of the suite. A release is the moment that stops being acceptable.
- [ ] **Full suite green on a clean checkout**, `PORTER_REQUIRE_UV=1`, with the count recorded.
- [ ] Every example builds, gates and publishes from a clean tree — the gallery *is* the acceptance test.
- [ ] Version bumped, tagged `v0.1.0`, pushed to `syalia-srl/porter`.

**Release gate — do not tag until all four are true:**
1. Every spec section is implemented or explicitly listed as deferred in `CHANGELOG.md`.
2. Every example builds and gates from a clean checkout.
3. No known silent-success path: every guard has a test that has been shown to fail without it.
4. The open risks in `docs/design-spec.md` are current — nothing claimed as verified that was not.
